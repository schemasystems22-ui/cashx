# CashX — bilingual transfer demo (العربية / English)

A pixel-oriented, fully interactive reproduction of the supplied CashX reference screens:
**Add Balance** (3 steps) and **Transfer** (3 steps), plus lightweight Home, Transactions and
My Account screens so the bottom navigation works.

> ⚠️ **This is a demonstration build.** It is not connected to any real wallet, bank or payment
> provider. It never asks for a PIN or OTP, never moves money and never claims to be licensed by
> the Central Bank of Egypt. Every transaction it shows is a simulation generated on this device.

---

## Run it

```bash
npm install      # once
npm run dev      # http://localhost:5178
```

Other scripts:

```bash
npm run typecheck   # tsc --noEmit
npm test            # vitest run (unit suite, no browser needed)
npm run test:watch  # vitest, re-runs on save
npm run build       # typecheck + production bundle into dist/
npm run preview     # serve the production build
```

The dev server is pinned to `127.0.0.1:5178` (see `vite.config.ts`) so it never collides with
another project on 5173.

**Demo credentials:** none. There is no login, no backend and no API keys.

## Installing it on a phone (PWA)

The build is an installable progressive web app: it works offline after the first visit and opens
full-screen with no browser chrome.

```bash
npm run build
npm run preview   # http://127.0.0.1:4178 — the service worker only exists in a build, not in dev
```

| Platform | How to install |
| --- | --- |
| Android (Chrome / Edge) | *Install app* in the ⋮ menu, or the install icon in the address bar |
| iOS / iPadOS (Safari) | Share → *Add to Home Screen* |
| Desktop (Chrome / Edge) | The install icon in the address bar |

What makes it installable, and where it lives:

* **Manifest** — generated by `vite-plugin-pwa` from `vite.config.ts`: name, `short_name`, `lang: ar`,
  `dir: rtl`, `display: standalone`, `orientation: portrait`, theme/background colours and the icon set.
  It also ships two **launcher shortcuts** (Transfer, Add Balance) that are just the deep links the
  router already understands.
* **Icons** — `public/assets/icons/`: 192 and 512 in the “any” purpose, a **maskable** 512 (full-bleed
  so Android's adaptive mask can cut any shape without clipping the mark) and a 180 px
  `apple-touch-icon`. iOS ignores manifest icons and reads that tag.
* **iOS meta** — `apple-mobile-web-app-capable` / `-status-bar-style=black-translucent` / `-title`, so
the home-screen bookmark opens standalone rather than inside Safari. Because the app then draws under
  the status bar, `.cx-header` adds `env(safe-area-inset-top)` to its padding — zero in a browser tab.
* **Service worker** — precaches the app shell, both bundles, the brand logos and the icons
  (`generateSW` builds the manifest from the actual build output, so hashed filenames are covered).
  Navigations fall back to the cached `index.html`, and the Google Fonts CSS and font files are
  runtime-cached, so the app opens offline with its real Arabic typeface rather than a fallback.
* **Zoom** — the viewport no longer sets `user-scalable=no` (a WCAG 1.4.4 failure). The text inputs are
  16 px, which is the threshold below which iOS Safari zooms the page on focus, so pinch-zoom is back
  without the jump.

## The fee rule (single source of truth)

`src/lib/config.ts` → `FEE_CONFIG`, applied by `src/lib/fee.ts`:

```
fee   = max( round(recipientAmount * 0.5%), minimumFeeMinor )
total = recipientAmount + fee
```

* `percentage: 0.5` — the label shown in the UI is generated from the config, never hardcoded twice.
* `minimumFeeMinor: 100` — a **configurable minimum of EGP 1.00**. It does not affect the reference
  example; set it to `0` to disable the floor. When it applies the summary keeps showing the real
  percentage, so the displayed number and the label never disagree.
* All money is stored as **integer minor units (piasters)** — no floating point arithmetic ever
  touches a currency value.

Reference example, reproduced exactly: recipient EGP 1,000.00 → fee EGP 5.00 → total EGP 1,005.00.

## Demo payment adapter (swap-in point for a real provider)

`src/lib/demoPayment.ts` implements the `PaymentAdapter` interface from `src/lib/types.ts`:

```ts
interface PaymentAdapter {
  readonly name: string;
  process(request: PaymentRequest): Promise<PaymentResult> // 'success' | 'failed' | 'pending'
}
```

The screens only ever talk to this interface. `createDemoPaymentAdapter({ simulateFailure })`
waits ~1.5 s and then returns a simulated outcome, so a real, authorised provider can be plugged in
later without touching a single screen. On the Confirm & Pay screen there is a **“Simulate a failed
transaction”** switch that exercises the failure path end-to-end (the receipt is stored with
`status: 'failed'` and the success screen is never shown).

## Language & direction

* **Arabic (default)** — `dir="rtl"`, Cairo typeface, Egypt locale with **Latin digits**
  (`ar-EG-u-nu-latn`) so amounts read `1,000.00 جنيه` exactly like the references.
* **English** — `dir="ltr"`, Inter, `EGP 1,000.00`.
* Switching language updates `<html lang>`/`<html dir>` instantly (no reload) and is persisted.
* Everything is driven by CSS logical properties, so labels, values, icons, arrows and the
  back/continue affordances flip with the direction.

Where the reference screens intentionally keep a **left-to-right order even in Arabic**, the demo
keeps it too (this is deliberate, not a bug): the wallet grids, the destination segmented control
and the step-progress rail all run left → right in both locales, matching the screenshots.

## Receipt export (image, PDF, QR, WhatsApp)

Both success screens show an invoice-style receipt with a QR code, a green **Send on WhatsApp** button
and an **Export receipt** button that opens a sheet with *Send on WhatsApp*, *Save as image*,
*Save as PDF* and *Share file* (falling back to a download where the browser cannot hand files to the
OS share sheet).

One model feeds all four output formats, so they cannot drift apart:

```
src/lib/receipt.ts        buildReceiptModel(tx, lang, t)  → heading, amounts, route,
                                                            rows, status, qr payload, disclosure
         ├─ on-screen markup          (the receipt screens themselves)
         ├─ src/lib/receiptImage.ts   canvas renderer     → PNG
         ├─ src/lib/pdf.ts            one-page A4 PDF wrapping that JPEG
         └─ buildReceiptTextFromModel plain text          → the wa.me message / clipboard
```

* **QR** — `src/lib/qr.ts` wraps the `qrcode` encoder and returns a plain module matrix, which is
drawn twice: as a single `<path>` on screen and as canvas rects in the export. Both therefore encode
the same payload at 25% error correction, with the four-module quiet zone the spec requires. The
payload is the transaction ID verbatim — `receiptQrPayload()` is the one line to change if it should
become a deep link instead.
* **PNG** — `receiptImage.ts` draws the card on a canvas at 2.5× (950×1781 px). It lays out on a fixed
  380-unit-wide grid and **measures the height** from the content: a transfer receipt has six detail
  rows and a top-up five, and an earlier fixed height put the QR code straight through the last rows.
  `measureReceipt` is exported so the non-overlap invariant is asserted in tests.
* **PDF** — `pdf.ts` writes the document by hand: five objects, one embedded JPEG via `DCTDecode`
  (so the compressed bytes are wrapped rather than re-encoded) and an xref table whose offsets are
  computed from real byte lengths. Validated by parsing the output with PDF.js in the test suite.
* **Text direction** — the canvas is drawn with `ctx.direction`, so Arabic is shaped and ordered by the
  platform text shaper. Values that are pure Latin runs (`010 1234 5678`) are drawn LTR on purpose:
  under an RTL paragraph direction their groups reverse to `5678 1234 010`, which is not what the
  reference screens show.
* **Fonts** — `ensureReceiptFonts()` awaits Cairo/Inter before drawing. Canvas text is rasterised at
  draw time and does not re-flow when a webfont arrives, so drawing early would silently fall back to
  a system face.

### Sending it on WhatsApp

`src/lib/whatsapp.ts` is deliberately two-tier, because WhatsApp has no web API that accepts a file:

| Platform | Route | What actually happens |
| --- | --- | --- |
| Android / iOS | `navigator.share({ files })` | The OS share sheet opens, WhatsApp is one of the targets, and the receipt **PNG arrives as a real attachment** — the same path the InstaPay app uses |
| Desktop | `wa.me/?text=…` | `wa.me` carries text only, so the message *is* the receipt (every line labelled, ID and status included) and the PNG is saved alongside it to attach. WhatsApp Web opens with the text already in the box, and the user presses send |

The card is rendered once through the same `receiptImage`/`receiptExport` path as *Save as image*, so the
attachment, the download and the PDF all show the same receipt. Nothing is sent on the user's behalf:
both routes hand off to WhatsApp and the user completes the send in their own app.

Added runtime dependency: `qrcode` (+16 kB gzipped). Dev-only: `pdfjs-dist`, used solely to validate
the generated PDF.

## Tests

`npm test` runs the Vitest suite over the pure logic that the acceptance criteria depend on. The
suite is deliberately headless — node environment, no jsdom, no React plugin — so it is fast and
has no browser dependency.

| File | Covers |
| --- | --- |
| `src/lib/fee.test.ts` | The reference case (EGP 1,000.00 → 5.00 → 1,005.00), the 0.5% rule, the minimum-fee floor and its exact boundary, zero/negative/fractional amounts, whole-piaster rounding, and `maxRecipientAmountFor` against a demo balance |
| `src/lib/format.test.ts` | Money in both locales (**Latin digits inside Arabic copy**), currency placement either side of the amount, the reference receipt chain rendered in `ar` and `en`, dates and times, phone grouping, amount-input grouping/parsing round trips, masking |
| `src/lib/ids.test.ts` | The `TXN-YYMMDD-HHMMSS` format including the reference example, zero-padding, the two-digit year, the 1-based month across all twelve months, and second-level resolution |
| `src/lib/qr.test.ts` | The payload, valid QR versions, determinism, and the three finder patterns plus the timing pattern — proving the symbol is well-formed rather than merely present |
| `src/lib/receipt.test.ts` | The shared model: per-flow rows and labels, tone assignment, route sides, status, locale differences, and the plain-text builder |
| `src/lib/receiptImage.test.ts` | Layout: band ordering, QR centring and clearance **from the last detail row**, height growth per row, and identical geometry in both languages |
| `src/lib/pdf.test.ts` | Header/trailer, the object graph, every xref offset resolving to its object header, JPEG embedding, A4 fit and centring, plus a PDF.js parse |
| `src/lib/a11y.test.ts` | The radiogroup keyboard mapping: arrow wrapping, the LTR/RTL swap of the horizontal pair, Home/End, ignored keys, and an exhaustive sweep proving no key can return an index outside the group |
| `src/lib/whatsapp.test.ts` | Which hand-off route is taken and what each one carries: native file share (attachment present, nothing downloaded), the `wa.me` fallback (image saved, link opened), a dismissed sheet reported as cancelled, a blocked popup reported as failed, and URL encoding that survives newlines and the `%` in `fee (0.5%)` |

Two things the suite pins down that are easy to get wrong later:

* **The floor's boundary.** `minimumApplied` is decided by the *rounded* fee, not the raw percentage,
  so it flips off one piaster before the arithmetic crossing point (EGP 198.00 rather than EGP 200.00).
  The fee itself is the floor throughout — only the flag changes, which is exactly what the flag means:
  *which rule produced this number*.
* **Id resolution.** `createTransactionId` is a pure function of the second it is given, so two calls
  within the same second are identical by design. The demo's ~1.5 s simulated payment delay keeps
  that off the critical path, but a real provider integration would need a stronger key.

Date assertions build dates from local-time components, so they hold in any timezone, and they read
ICU month names — Node ships full ICU by default (Node 13+), which is what makes `أكتوبر` resolvable.

## Deep links (the address bar is the router)

Every screen and flow step is addressable, and the address bar is kept in sync in both directions.
The whole scheme lives in `src/lib/route.ts`.

```
?lang=en                                            → Home, English
?screen=transfer&step=2&lang=en                     → Transfer, Confirm & Pay
?screen=addBalance&step=2&lang=ar                    → Add Balance, Transaction Summary
?screen=transactions&lang=en                        → Transactions list
?screen=transaction&id=TXN-261011-175503&lang=en     → that receipt
?screen=account&lang=en                             → My Account
```

* **Keys** — `screen`, `step`, `lang`, and `id` for a receipt. `route`/`page`/`view`, `language`,
  and `tx` are accepted as synonyms, and spellings are forgiving: `add-balance`, `addBalance` and
  `add_balance` all work, as do `step=2`, `step=confirm` and `step=pay`.
* **Missing or malformed input is never an error.** An unknown `screen` opens Home, a receipt link
  with no `id` opens the list, an unknown receipt `id` shows the existing “Transaction not found”
  state, and anything not spelled above is dropped. The address bar is then rewritten to the
  canonical form, so it always round-trips.
* **`step=3` is addressable but not restorable.** The receipt screen can only render on top of a
  transaction this session confirmed, so a `step=3` link opens step 2. Step 3 *is* written while
  the receipt is on screen — the URL never under-reports where you are.
* **Steps are owned by the route, not the screen.** `useFlowStage` reads steps 1–2 back from the
  route and only keeps the transient stages (`processing`, `success`, `failed`) local. That is why
  re-entering a flow through the bottom nav resets it to step 1 *and* the URL agrees, instead of the
  screen staying on Confirm while the address bar claims step 1. Moving between steps never remounts
  the screen, so entered form data survives Back and Edit Details.
* **History.** Moving between screens (`Home` → `Transfer` → a receipt) pushes, so the browser Back
  button walks those screens. Flow step changes, language changes and the transient `processing`
  stage replace instead, so the history stack stays meaningful and a spinner is never a back target.
  `popstate` re-derives the whole screen from the URL, which is also how a link pasted into the
  same tab works.
* **Language.** `?lang=` wins over the stored preference on load, and every URL carries `lang`, so a
  link you copy reopens in the language you sent it in.
* Query parameters the scheme does not own are dropped when canonicalising. If you add a URL flag
  later (e.g. a reduced-motion override), teach `serializeLocation` about it.

## Motion

Every animation is CSS-driven and keyed off a remount, so nothing depends on timers in React
state. Durations and easings live in `src/styles/tokens.css` (`--cx-dur-press/fast/base/step/slow`,
`--cx-ease-out`, `--cx-ease-pop`, `--cx-press-scale`).

| Launch | The splash (see below) |
| Screen switch | A real cross-fade through the View Transitions API, so the outgoing *and* incoming screens are on screen together — a keyed CSS animation can only fade the new one in, because the old screen is already unmounted |
| Flow step change | `StepTransition` remounts the step body with `cx-enter` and smooth-scrolls the panel back to the top |
| Success checkmark | The badge pops (`cx-pop`), a soft halo expands behind it (`cx-halo`), then the tick strokes itself in via `stroke-dashoffset` on `cx-draw` |
| Amounts | `useCountUpState` eases the demo balance and the success-screen balance up to their real value in integer piasters and reports `counting`, which drives the `.cx-counting` lift while the number is still moving. A `setTimeout` safety net snaps to the true value, so a throttled frame can never leave a wrong figure on screen |
| Staggered rows | Receipt detail rows and transaction-list items enter with a 40 ms per-row delay |
| Press feedback | Buttons, wallet tiles, chips, nav items, stars and list rows scale to `--cx-press-scale` with a 110 ms transform transition; hover raises primary/secondary buttons, tiles and rows |

### The launch splash

`src/components/Splash.tsx` + the `.cx-splash*` block in `base.css`: the lockup scales up out of a
violet bloom and a magenta light band drifts across the frame while the whole scene pushes in slowly
(`cx-splash-cam`), a specular highlight sweeps over the mark (`mix-blend-mode: screen`), the tagline
rises, and a thin rail fills at the bottom. It then dissolves upward — scale, blur and fade — into the
app, which has been mounting behind it the whole time.

* **Once per browser session** (`sessionStorage`, read and written separately so React's StrictMode
double-invoke cannot make the answer differ). A splash on every navigation is a tax, not a flourish.
* **Skippable** — any pointer, key, wheel or touch event cuts straight to the dissolve.
* **The rail's fill and the hold are one number.** `HOLD_MS` drives the timer *and* the CSS custom
  property, so the bar can never finish before or after the exit.
* **The app behind it is `inert`** for the duration: nothing under the overlay is reachable by tab or
  by assistive technology until the intro is done.
* **Exit is timer-driven, never `animationend`** — the overlay is guaranteed to come down even if the
  animation never ran.

### Cross-fades between screens

`src/lib/viewTransition.ts` runs every navigation inside `document.startViewTransition`, flushing the
React commit synchronously so the browser snapshots the finished DOM. The app frame is named
`cx-frame`, so only the phone frame animates and the page behind it stays put; `html[data-cx-vt]`
tells the stylesheet whether this is a tab change, a push into a receipt, or a flow step (a step is a
quicker, scale-free version). While a transition is in flight the keyed animations step aside so
nothing is animated twice. Where the API is missing — or the user asked for reduced motion — the update
just runs and the keyed CSS enter animation takes over.

### `prefers-reduced-motion`

Honoured everywhere, in three layers:

1. `usePrefersReducedMotion()` (in `src/components/motion.tsx`) short-circuits the JS-driven
   animations — `useCountUpState` returns the final value with `counting: false` immediately, and
   `StepTransition` jumps instead of scrolling smoothly.
2. A global `@media (prefers-reduced-motion: reduce)` block (kept last in `base.css` so it always
   wins) collapses every animation and transition to `0.001 ms`.
3. The same block then strips the decorative animations outright (`animation: none; opacity: 1;
   transform: none`) for anything that uses `animation-fill-mode: both`, so **content can never be
   stuck invisible** waiting for an animation that no longer runs.

To check it in a browser: DevTools → Rendering → *Emulate CSS media feature prefers-reduced-motion*.

## Accessibility

### Focus follows the view, not the click

Both a screen change and a flow step change unmount the control that was just used, which would drop
focus onto `<body>` and restart a screen-reader or keyboard user at the top of the document. Two
scripted focus targets fix that:

* **Screen change** — `App.tsx` focuses the keyed screen container, which carries
  `role="group"` and an `aria-label` naming the screen (`Home`, `Transfer`, `Transaction Details`, …).
* **Step change** — `StepTransition` focuses the step container, labelled through `a11y.stepOf`:
  *“Step 2 of 3: Confirm & Pay”*. Success and failure steps name the **outcome** rather than the step
  number (*“Step 3 of 3: Transfer Successful!”*), so the result of a simulated payment is announced by
  the focus move itself. The two effects are ordered so they never fight: on a screen change the
  parent effect wins, on a step change only the child re-runs.

Both containers carry `tabIndex={-1}` and `.cx-screen:focus` / `.cx-body__inner:focus` set
`outline: none`: they are reachable only programmatically, so a ring there would be noise, and every
real control keeps its own indicator.

### Live regions for the things focus cannot carry

A persistent, visually hidden pair of regions (`role="status"`, one `polite`, one `assertive`) lives in
`App.tsx` for the whole session and is driven by `announce()` in the store. They stay mounted and only
their child changes — a region inserted *together with* its content is routinely ignored. Reserved for
status that has no focus target of its own: toasts and copy confirmations (polite), a failed simulated
top-up (assertive), and the language switch, which is announced **in the language just chosen**.

### Keyboard

The wallet tiles, the destination segmented control and the star rating implement the WAI-ARIA
radiogroup contract through one shared hook, `useRovingRadioGroup` in `src/lib/a11y.ts`: a single Tab
stop for the group, arrows that move *and* select with wrapping, Home/End, and the left/right pair
swapped under RTL. The destination picker is a radiogroup rather than the `role="tab"` it used to be —
there are no tab panels behind it, and `role="tab"` promises Tab-key navigation that does not exist.

Sheets are real modal dialogs (`role="dialog"`, `aria-modal`, `aria-labelledby` on the visible title)
with focus moved in on open, Tab cycling inside the panel in both directions, Escape to close, and
focus returned to the trigger — but only if that trigger is still in the document, since a sheet can
outlive the screen that opened it.

Validation sends focus to the first field that needs fixing, and each field is wired with
`aria-invalid` plus `aria-describedby` pointing at its live hint or its error, so the message is heard
in context instead of being left behind on the button that was pressed.

### Contrast

Measured against white, the lilac surface (`#f4eeff`) and the stepper's inactive dot (`#f1eef8`).
Three tokens were failing WCAG AA and were darkened; the *hues* and every decorative use are
untouched, so the reference artwork reads the same:

| Token | Was | Now | Worst case |
| --- | --- | --- | --- |
| `--cx-text-2` (hints, subtitles, disclosures) | `#85839a` | `#5f5c73` | 5.7:1 (was 3.2:1) |
| `--cx-text-3` (nav labels, stepper labels, chevrons) | `#a5a2b8` | `#6b6880` | 4.7:1 (was 2.2:1) |
| success green in **text** | `#159447` | `--cx-green-text: #0f7a39` | 5.1:1 (was 3.7:1) |

The green split matters: `--cx-green` still draws the checkmark, its halo and the soft fills exactly
as the reference shows them, while `--cx-green-text` is the darker sibling used for values. Two
contextual rules fix the dark header, where a single token cannot serve both surfaces: the Transfer
stepper labels take `--cx-on-dark-dim` (9.8:1) with the active label in white (19.9:1 — it was primary
purple at 2.4:1 on the header gradient), and focus rings inside `.cx-header` are white instead of
purple.

`.cx-amount__input` and `.cx-input` set `outline: none`, which previously left a focused field with
**no** visible indicator at all. The wrappers now show a purple border plus a 3 px halo on
`:focus-within`.

Brand wordmarks inside the wallet tiles (Vodafone, etisalat, orange, we) are logotypes and are exempt
from text-contrast rules; the tiles are stand-ins for licensed artwork regardless.

### Structure

Every screen renders exactly one `role="main"` landmark and an `h1`. Two screens needed help: Home
and Transfer carry no visible title in their headers, so each gets a visually hidden `h1` naming the
screen, and the Transfer form's section labels became real `h2`s, giving the form a heading outline
instead of starting at an `h2` with no `h1` above it.

### What is verified, and how

Checked in the running app rather than asserted from the CSS: arrow keys moving **and** selecting in
both directions and both languages; Enter activating the focused Continue button; focus landing on
the step container with the right accessible name after each transition; the copy toast reaching the
polite region; the language switch announcing in the new language; validation moving focus to the
invalid field with `aria-invalid` + `aria-describedby` set; the dialog trapping Tab forwards and
backwards and restoring focus on Escape; a 14-stop tab order on Home with no positive `tabindex`; and
the computed colour of every rendered text node against its real background.

One caveat worth stating: `:focus-visible` only matches while the webview itself has OS focus, so the
focus-ring checks above were read after a real click had focused the page. Worth a quick manual pass
with a screen reader (VoiceOver or NVDA) — automated checks confirm the DOM contract, not the
spoken experience.

## Brand assets

* **The CashX mark.** `public/assets/cashx-app-icon.jpg` is the supplied artwork, byte-for-byte, and is
  the source for every app icon. `src/components/CashXLogo.tsx` redraws the X as two interlocking bands
  whose proportions were **measured from that file** (white band: flat end 26/100, apex at 58/100, notch
  at 32/100, height 84/100; the violet band is its mirror), so the in-app mark matches the artwork
  rather than being a generic X icon.
* **Operator logos.** Vodafone Cash, Etisalat Cash, Orange Cash, WE Pay and InstaPay are the real
  supplied image files, served from `public/assets/brands/`. They arrive at five different aspect
  ratios with very different amounts of built-in padding — the Orange file is a wide card whose mark
  fills 44% of the canvas, the WE file a circle with no padding at all — so each is fitted into the
  same white rounded tile and optically normalised with a **per-brand zoom** (`.cx-logo--vodafone` …
  `.cx-logo--instapay` in `components.css`). Every zoom targets the same *visible height*, which is
  what makes a wide glyph, a circle and a square read as one set:

  | Tile | Vodafone | Etisalat | Orange | WE |
  | --- | --- | --- | --- | --- |
  | 46 px (wallet grid, route pair) | 30.5 | 29.4 | 30.8 | 30.8 |
  | 52 px (Add Balance grid) | 34.4 | 33.3 | 34.8 | 34.8 |
  | 30 px (chips, receipt rows) | 19.9 | 19.2 | 20.1 | 20.1 |

  Measured from the rendered tiles — `visible height = contentShare × contain-scale × zoom` — and no
  tile clips.
* **InstaPay is one file, shown whole, at every size.** Its lockup stacks a mark over a wordmark
  (283×179 in a 447 square), so matching the others' 30 px *height* would need 47 px of width and clip.
  It is instead taken to the same edge clearance as the widest of the others — 43.1 px of a 46 px tile,
  where Etisalat sits at 43.5 — which is as large as the whole logo can go. An earlier version cropped
  the wordmark away on the small tiles to keep the mark legible; seen next to four logos that do keep
  theirs, that reads as a missing image rather than as a smaller one, so the crop is gone.
* **Bank Account** has no supplied artwork, so it stays a drawn icon from the line-icon set.

**Regenerating the app icons** after a logo change:

```bash
python tools/make-icons.py    # rewrites public/assets/icons/ (needs Python 3 + Pillow)
```

The script re-reads what it wrote before exiting: a PNG whose zlib checksum is wrong still renders in
Chromium but is rejected by stricter decoders, so a derived asset can arrive broken while looking fine
in the browser. That is not hypothetical — it has happened in this repo.

## Remaining visual mismatches

1. **The iOS status bar** (9:41, signal, battery, home indicator) in the references is OS chrome and
   is deliberately not reproduced.
2. **Arrow/slot sides on primary buttons.** The reference places the brand tile on the left and the
   forward arrow on the right in Arabic (Add Balance, Pay), but the Transfer *Continue* button in
   the reference has its arrow on the left. The demo uses one consistent arrangement (brand/leading
   affordance first, forward arrow last) in both locales.
3. **Quick-amount order.** The references disagree with each other (`+5,000 … +500` on Add Balance
   step 2, `+500 … +5,000` on Transfer step 1). The demo keeps one order; it matches the Add Balance
   reference in Arabic and the Transfer reference in English.
4. **Selected-wallet checkmark corner.** The 2×2 grid reference puts the badge on the top-right of
   the tile, the 4-across reference on the top-left. The demo uses the top-right in both.
5. **Step rail length.** The reference rail is inset ~8 px further than the demo's on the outer
   steps (the demo centres each label over its dot, which the reference does too).
6. **Operator logos** are the supplied image files, so a couple carry a white background where the
   reference shows them on the tile's own white — invisible in practice, but not pixel-identical.
7. **InstaPay's wordmark is small on the 30–40 px tiles.** The whole lockup is shown at every size (see
   *Brand assets*), and at 30 px its wordmark is ~4 px tall — legible as a shape, not as text. Sizing it
   to match the other marks would need 47 px of tile width, and cropping it away makes the tile look
   like a failed image next to four complete ones.
8. Header/section sizes are within ~2–8 px of the reference at a 414 px frame; the reference's own
   screenshots are 740 px wide for the same composition.
9. **Secondary and tertiary text is darker than the reference.** The reference's two dimmest greys
   measure 3.7:1 and 2.5:1 on white — below WCAG AA — so they were darkened to 5.4:1 and 4.7:1. The
   same applies to success green used as *text*; the checkmark, halo and soft fills keep the exact
   reference value. See the Accessibility section for the token table.
